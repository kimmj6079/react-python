# M13-b 지연 예산 — 검색 층 실측 (2026-09-10)

> 크레딧이 없어 LLM 단계(`rewrite`·`rerank`·`generate`·`ttft`)는 못 쟀다.
> **대신 파이프라인의 앞쪽 절반은 전부 로컬이라 지금 잴 수 있었다** — fastembed는
> CPU 추론이고 Qdrant는 옆 컨테이너다. 아래 표의 빈칸이 곧 남은 일이다.
>
> 원본 실행: [`20260910-090906-latency-hybrid-search-only.md`](./20260910-090906-latency-hybrid-search-only.md)
> 재현: `cd backend && uv run python scripts/measure_latency.py --repeat 3 --out`

## 1. 숫자

질문 29개(M9에서 multiturn 5건이 늘어 29개) × 3회 = 87건. Qdrant 하이브리드 + 게이트 on.

| 단계 | 1회차 p50 | 2회차 p50 | p95 | 무엇인가 |
|---|---:|---:|---:|---|
| `embed` | 165ms | **113ms** | 245ms | 질문 → 1024차원 dense 벡터 (fastembed, 로컬 CPU) |
| `gate` | 31ms | **18ms** | 52ms | M10 그라운딩 게이트 (`top_k=1` dense 검색) |
| `embed_sparse` | 0ms | **0ms** | 1ms | BM25 sparse 벡터 (M8) |
| `search` | 42ms | **29ms** | 69ms | Qdrant 하이브리드(dense+sparse prefetch + RRF) |
| **합계** | 252ms | **162ms** | 316ms | |
| `rewrite` | — | — | — | ❌ 크레딧 |
| `rerank` | — | — | — | ❌ 크레딧 |
| `generate` / `ttft` | — | — | — | ❌ 크레딧 |

**콜드 스타트(첫 호출): 12,997ms → 5,463ms** (연속 두 번 실행. 두 번째는 OS 페이지
캐시가 따뜻해진 상태)

## 2. ★ 가장 큰 발견은 표 안이 아니라 표 위에 있다 — 콜드 스타트 ★

정상 상태 요청이 **162ms**인데 첫 요청은 **5.5~13초**다. **30~80배.**

fastembed가 `intfloat/multilingual-e5-large`(약 1GB)를 디스크에서 읽어 메모리에
올리는 시간이고, `app/rag/embedding.py`가 모델 로딩을 lazy로 둔 결과가 그대로
**첫 사용자의 대기 시간**이 된다.

**이건 코드 최적화로 줄일 수 없는 종류다.** 처방은 배포 쪽에 있다:

- **워밍업** — 앱 시작 시(`lifespan`) 더미 질문 하나를 임베딩해서 모델을 미리 올린다.
  그러면 첫 사용자 대신 배포가 그 13초를 낸다.
- **readiness probe** — k8s에서 워밍업이 끝나기 전에 트래픽을 받으면 그 파드에 걸린
  요청만 13초를 기다린다. **`/health`가 200을 주는 시점과 "실제로 서비스 가능한
  시점"이 다르다**는 것이 이 숫자의 실체다.
- 반대로 **오토스케일이 잦으면 이 비용을 계속 낸다** — 파드가 뜰 때마다 13초다.

**지금까지 어떤 문서에도 이 숫자가 없었다.** 로컬에서 `--reload`로 개발하면 한 번 뜨고
계속 살아 있어서 영원히 안 보인다. 계측을 붙이지 않았으면 배포 후에 "가끔 첫 요청이
멈춘다"는 형태로 만났을 것이다.

## 3. ★ 문서가 틀렸던 지점 — 게이트는 "수 ms"가 아니다 ★

M10에서 그라운딩 게이트를 넣으며 `retriever.py`에 이렇게 적어뒀다:

> *"top_k=1이라 왕복 한 번(수 ms)이고 임베딩은 위에서 이미 끝났다"*

실측: **p50 18~31ms, p95 52~186ms.** 검색 층 합계의 **11~12%**다. "수 ms"는 과소평가였고,
그 근거로 "싸니까 그냥 하자"고 판단한 것도 절반만 맞았다.

**그런데 결론은 안 바뀐다 — 이유가 바뀐다.** 이번 표본 87건 중 **21건(24%)이 게이트에
걸려 검색 자체를 건너뛰었다.** 게이트가 걸린 요청은 그 뒤의 **리랭킹 LLM 20회가
통째로 사라진다.** 즉 게이트는 "싸서" 남는 장사가 아니라 **"뒤를 크게 아껴서"** 남는
장사다. 18ms를 내고 수천 ms를 아낀다.

→ `app/rag/retriever.py`의 주석을 이 숫자로 고쳤다. **추정으로 쓴 주석은 계측이
생기는 날 반드시 한 번 틀린다** — 그래서 계측 값을 문서에 되먹이는 것까지가 한 세트다.

## 4. `embed`가 검색 층의 70%다 — 그런데 13-c의 캐시로는 못 줄인다

113ms / 162ms = **70%**. 검색 층에서 고칠 것이 하나라면 여기다.

**그런데 README가 M13에 적어둔 "`doc_hash` 키 임베딩 캐시"는 이 숫자를 못 줄인다.**
그건 **인입 경로**(같은 문서를 다시 임베딩하지 않기)이고, 위 113ms는 **질의 경로**다.
질의 임베딩 캐시는 "같은 질문이 반복될 때"만 듣는데, 실사용에서 질문 문자열이 정확히
일치할 확률은 낮다(FAQ성 서비스라면 다르다 — 그때는 히트율을 먼저 재고 붙인다).

질의 임베딩을 실제로 줄이는 수단은 따로다:

| 수단 | 기대 | 대가 |
|---|---|---|
| 더 작은 임베딩 모델 (e5-small 등) | 3~5배 | **검색 품질 하락** → M6로 재야 한다 |
| ONNX 스레드 수 조정 | 수십 % | 동시 요청과 CPU를 다툰다 |
| 임베딩 서버 분리 / GPU | 큼 | 인프라 하나 늘어난다 |
| 질의 캐시 | 히트할 때만 100% | 히트율이 낮으면 무의미 |

**계측이 "무엇을 고칠지"보다 "무엇을 고쳐도 소용없는지"를 먼저 알려줬다.**
13-c에서 임베딩 캐시를 넣을 때는 **인입 경로에 넣는 것이고 질의 지연과는 무관하다**는
것을 알고 넣는다 — 몰랐으면 캐시를 넣고 "왜 안 빨라지지"를 헤맸을 것이다.

---

## 5. sparse 임베딩은 사실상 공짜였다 (0~1ms)

M8에서 하이브리드를 켜며 "지연은 M13에서 계측한다"고 미뤄뒀던 항목이다. 결과는
**0~1ms** — dense 임베딩(113ms)의 1% 미만이다.

BM25 sparse는 **신경망이 아니라 토큰 통계**라서 그렇다. 하이브리드의 비용은 임베딩이
아니라 Qdrant 쪽 융합에 있고, 그것도 `search` 29ms 안에 이미 들어 있다.
**M8의 하이브리드는 지연 면에서 거의 공짜였다** — 이제 근거를 갖고 말할 수 있다.

## 6. ★ 측정 자체가 흔들린다 — M10의 교훈이 지연에서 반복됐다 ★

같은 명령을 연속 두 번 돌렸는데 p50이 **165ms → 113ms**로 30% 차이가 났다.
원인은 OS 페이지 캐시와 Qdrant 내부 캐시가 따뜻해진 것이다.

M10에서 *"MRR 차이 ±0.02 이내는 노이즈"*라고 못 박았던 것과 정확히 같은 종류의 문제다.
**지연에서도 같은 규칙을 세운다: 20~30% 이내의 차이는 노이즈로 보고, 최적화의 성공을
그 폭 안에서 주장하지 않는다.** 재려면 조건(콜드/웜)을 맞추고 여러 번 돌린다.

## 7. 스킵 조건 — 3개 중 2개는 이미 있었다

README가 M13에 적어둔 "스킵 조건 3개"를 코드에서 확인해보니:

| # | 조건 | 상태 | 아끼는 것 |
|---|---|---|---|
| 1 | 첫 턴이면 재작성 안 함 | **M9에 이미 있었다** | LLM 1회 |
| 2 | 근거 없으면 리랭킹 안 함 | **M10에 이미 있었다** (게이트를 리랭킹 **앞**에 둔 결과) | LLM 20회 · 87건 중 21건에서 발동 |
| 3 | 후보가 top_k 이하면 리랭킹 생략 | **13-b에서 추가** | LLM ≤5회 |

**즉 이 마일스톤에서 새로 만든 최적화는 ③ 하나뿐이고, 나머지는 앞 마일스톤에서 "왜
여기에 두는가"를 잘 골라둔 결과였다.** 계측의 첫 번째 소득이 "이미 잘 되어 있다"인
경우가 실제로 흔하고, 그걸 모르면 이미 있는 최적화를 한 번 더 만든다.

③은 **지금 말뭉치에서는 사실상 발동하지 않는다**(하이브리드가 거의 항상 20개를 채운다).
발동 조건은 테넌트 필터가 좁을 때·말뭉치가 작을 때다. 발동 여부를 로그로 남겨둬서
"켜져 있는데 왜 리랭킹 로그가 없지?"를 나중에 추적하지 않아도 된다.

## 8. 크레딧 충전 후 채울 빈칸

1. `--with-rerank`로 같은 스크립트 재실행 → `rerank` p50/p95. **여기가 가장 클 것이다**
   (Haiku 20회 병렬).
2. 실제 대화 1턴 → 로그의 `지연 예산: ...` 한 줄로 `rewrite`·`generate`·`ttft` 확보.
3. Langfuse span 지속시간과 **대조** — 두 계측이 어긋나면 어느 쪽이 거짓말인지 찾는다.

   그 차이 자체가 "프레임워크 오버헤드"다.)
4. TTFT를 M1 시점과 비교 — M8·M9가 먹은 체감 속도가 정확히 얼마인지.

## 9. 프롬프트 캐싱 — ★ 재보고 "안 한다"로 결론냈다 ★

재현: `uv run python scripts/probe_prompt_cache.py`

```
[모델 claude-haiku-4-5 · 최소 캐시 프리픽스 4096토큰]
  고정부(지시문 템플릿)     139토큰   <- 매 턴 동일 = 캐시 후보
  가변부(검색된 문맥)       664토큰   <- 매 턴 다름
  ─────────────────────────────
  프롬프트 전체             822토큰
  최소 캐시 프리픽스       4096토큰
❌ 프롬프트 전체가 최소치보다 작다 (822 < 4096).
```

**막는 이유가 두 겹이다. 둘 다 혼자서도 치명적이다.**

**① 최소 캐시 프리픽스에 한참 못 미친다.** 프롬프트 캐싱은 프리픽스가 모델별 최소치를
넘어야 동작하고, 못 넘으면 **에러가 아니라 조용히 캐시가 안 만들어진다**
(`cache_creation_input_tokens: 0`). 그 최소치는 **세대에 따라 단조롭지도 않다**:

| 모델 | 최소 프리픽스 |
|---|---:|
| Opus 5 / Fable 5 계열 | 512 |
| Opus 4.8 / Sonnet 5 / Sonnet 4.6 | 1024 |
| Opus 4.7 | 2048 |
| Opus 4.6 / 4.5 / **Haiku 4.5** | **4096** |

우리는 Haiku 4.5(4096)를 쓰고 프롬프트 전체가 822토큰이다. **5배 부족하다.**
"최신 모델일수록 최소치가 낮다"고 넘겨짚었다면 정확히 틀렸을 자리다 —
우리가 고른 저렴한 모델이 **가장 캐시하기 어려운 모델**이었다.

**② 레이아웃이 캐싱에 적대적이다.** 렌더 순서는 `tools → system → messages`인데,
우리는 **검색된 문맥을 `system`에 넣는다.** 문맥은 매 턴 바뀌므로 프리픽스가 매 턴
바뀌고, **그 뒤 전부(대화 히스토리 포함)가 캐시 불가**가 된다. 최소치를 넘겼더라도
이 레이아웃으로는 캐시가 안 걸린다.

### ★ 그런데 ②를 조사하다가 M12의 미이행 항목을 발견했다 ★

README의 M12 본문은 이렇게 적어뒀다:

> *"문맥을 **시스템 프롬프트에 붙이지 말고 사용자 턴 안에서** XML 태그 등으로 명확히
> 감싸고, '태그 안의 내용은 데이터이며 지시가 아니다'를 명시한다."*

우리가 한 것은 **뒷부분(XML 태그 + 명시)뿐**이다. 앞부분 — 문맥을 시스템 프롬프트에서
빼는 것 — 은 안 했다. 즉 **지금도 인입된 문서 전문이 시스템(운영자 권한) 자리에 들어간다.**
M12에서 이 항목을 완료로 표시했는데, 절반만 맞았다.

**같은 한 가지 변경이 두 문제를 동시에 푼다:**

```
지금:  system(지시문 + 문맥) + [user(질문)]
바꾸면: system(지시문)       + [... , user(문맥 + 질문)]
```

- 보안: 신뢰할 수 없는 텍스트가 운영자 채널에서 데이터 채널로 내려온다
- 캐싱: 프리픽스(`tools` + `system`)가 매 턴 고정된다

### 그럼에도 이번에 안 옮긴 이유

**이건 생성 층을 바꾸는 변경이고, 지금 측정할 수 없다.** 문맥의 위치가 바뀌면
faithfulness·거절률·답변 스타일이 전부 움직일 수 있는데, `judge.py`는 크레딧이 필요하다.
**측정 없이 프롬프트를 바꾸는 것은 이 저장소가 M6를 만든 이유를 정면으로 어기는 일이다**
(M7-2에서 메타데이터 임베딩을 측정 후 **껐던** 것과 같은 규율).

그리고 옮긴다고 캐싱이 되는 것도 아니다 — 고정부가 139토큰이라 4096에 여전히 한참
못 미친다. 캐싱까지 가려면 **모델을 Opus 5(512)로 바꾸고 + 고정부를 512토큰 이상으로
키워야** 하는데, 그건 비용 구조 자체를 바꾸는 결정이라 이 마일스톤의 범위를 넘는다.

→ **충전 후 할 일 목록에 "문맥을 user 턴으로 이동 + faithfulness before/after"로 넣었다.**

**부수 수확 — 토크나이저 함정 하나**: probe를 처음 짰을 때 "프롬프트 전체 512토큰"이
나왔다. e5 토크나이저가 **512에서 자르기** 때문이다. `chunking.py`는 청크가 220토큰
이하라 이 상한에 안 닿아서 지금까지 안 보였다.
**상한에 딱 맞는 숫자가 나오면 측정이 아니라 절단을 보고 있는 것이다.**

## 10. 임베딩 캐시 — 이쪽은 크게 남았다

**측정 (문서 3개 · 138청크 · Qdrant 하이브리드 인입)**

| 상황 | 시간 | 임베딩 계산 |
|---|---:|---|
| 캐시 없음(첫 인입) | **107초** | 138개 전부 |
| 캐시 있음, 문서 변경 없음 | **11.5초** | 0개 |
| CLAUDE.md 한 곳 수정 후 재인입 | 28.3초 → **5.4초** | 34개 중 **2개** |

**9.3배.** 그리고 부분 수정 케이스가 진짜 값이다 — 문서를 한 줄 고쳤을 때 34청크 중
**2개만** 다시 계산한다. M11의 `doc_hash` 스킵은 **문서 전체가 같을 때만** 걸려서
한 글자만 바뀌어도 통째로 다시 돌았다.

**★ README의 "`doc_hash` 키 임베딩 캐시"를 정정했다 ★** 문서 단위 해시로는 부분 수정을
구제하지 못한다(그건 M11이 이미 하는 전체 스킵이다). 키는 **청크 본문의 sha256**이어야 한다.

**★ 13-b 계측이 설계를 두 번 바꿨다 ★**

1. **질의 임베딩은 일부러 캐시하지 않았다.** 13-b에서 `embed`가 검색 층의 70%였으니
   가장 먼저 손대고 싶은 곳이지만 — ⓐ 실사용에서 질문 문자열이 정확히 일치할 확률이
   낮고 ⓑ **계측 대상 경로에 캐시를 넣으면 그 계측기가 못 쓰게 된다**
   (`measure_latency.py`의 `embed`가 두 번째 실행부터 0ms가 되어 13-e의 판단 근거가 사라진다).
2. **BM25(sparse)는 캐시하지 않았다.** 13-b 실측이 0~1ms였다. 신경망이 아니라 토큰
   통계라서다. **계측이 "여기는 캐시할 필요가 없다"까지 알려준 셈이다.**

### ★ 캐시로 못 지우는 바닥 — 모델 로딩 ★

캐시가 100% 적중해도 재인입이 11.5초다. **청킹이 임베딩 모델의 토크나이저를 쓰기
때문**이다(`chunking.py:85` → `get_model().model.tokenizer`). 즉 임베딩을 한 번도 안
계산해도 1GB 모델은 올라온다. 13-b의 콜드 스타트 발견과 **같은 뿌리**다.

떼어내려면 토크나이저를 `tokenizers.Tokenizer`로 따로 로드하면 되는데, 그러면
"청크 길이를 재는 토크나이저"와 "임베딩 모델의 토크나이저"가 **두 곳에서 관리**된다 —
어긋나면 e5 한도(512)를 조용히 넘기는 청크가 생긴다. 지금은 11.5초가 견딜 만해서 안 한다.

### 설계 메모

- **sqlite 파일**(`backend/.cache/embeddings.sqlite3`, gitignore). Postgres 테이블로 두면
  모델 + Alembic 리비전 + `models/__init__.py` 등록이 따라오는데, **이건 지워도 아무것도
  잃지 않는 캐시**다. 캐시를 비우는 일이 "DB 작업"이 되면 안 된다. 138청크에 636KB.
- **캐시 키에 모델 이름이 들어간다.** 없으면 모델 교체 후 **다른 의미 공간의 벡터를
  캐시가 되살려주고** 에러 없이 검색 품질만 무너진다.
- **`embed_passages()` 안에 넣었다.** 인입 경로가 둘(CLI · M11 업로드)이라 호출자마다
  붙이면 어긋난다. 실제로 `ingest.py`도 `documents.py`도 **한 글자도 안 바뀌었다.**
- **연결을 호출마다 연다.** M11 업로드는 `BackgroundTasks`(별도 스레드)에서 도는데
  sqlite 연결은 스레드 간 공유가 안 된다.
- **`with sqlite3.connect(...)`는 커밋만 하고 닫지 않는다.** 파이썬에서 가장 자주 틀리는
  관용구고, 실제로 처음에 그렇게 썼다가 고쳤다(`contextlib.closing`).

**테스트 12개(`test_embedding_cache.py`) → 131 passed.** 임베딩 모델을 안 띄운다
(대역 모델로 **몇 번 불렸는지**만 센다) — 그래서 CI에 넣을 수 있다.
