## 2. ★ 계획이 틀렸다 — heading_path 부착은 역효과였다 ★

`chatbot/README.md`의 M7 계획에는 이렇게 적혀 있었다:

> 청크 본문 맨 앞에 `heading_path`를 **문자열로 같이 넣어 임베딩**한다
> (위 실패 ②의 가장 싼 처방 — **코드 세 줄로 지표가 눈에 띄게 움직이는 경우가 많다**).

**우리 말뭉치에서는 반대였다.** 붙인 ④·⑤가 안 붙인 ②·③보다 나쁘다. 특히 ⑤(헤딩을
지우고 경로로 대체 — 계획이 그린 그림에 가장 가까운 설정)가 **다섯 중 최악**이다.

**가설 세 가지** (확정이 아니라 가설이다 — 이 말뭉치에서 관찰한 것뿐이다):

1. **청크가 짧고 제목이 길다.** 평균 133토큰짜리 청크에
   `"CLAUDE.md > 작업 방식 — 이 저장소는 학습용이다"`(20토큰 남짓)를 붙이면 **15%가 제목**이다.
   그러면 같은 섹션의 청크들이 서로 가까워지고 **각자의 본문에서 멀어진다** — 검색은
   "이 섹션인가"가 아니라 "이 문장인가"를 물어야 하는데 반대로 간다.
2. **한글 제목의 토큰 밀도.** 한글은 문자당 0.55토큰, 영어는 0.19토큰(실측). 영어 문서로
   쓰인 원 기법의 감각보다 **제목이 3배 무겁다.**
3. **문서가 3개뿐이다.** heading_path의 큰 값은 "많은 문서 사이에서 어느 문서인가"를
   구분하는 것인데, 그건 `source`가 이미 하고 있다.

**그래서 기본값을 껐다** (`ingest.py`의 `embed_heading_path=False`). 지우지 않고 플래그로
남긴 이유는 말뭉치가 커지거나 영어 문서가 늘면 결론이 달라질 수 있어서다 —
`--embed-heading`으로 언제든 다시 잰다.

> **★ 이게 M6를 먼저 만든 값이다 ★** 계측기가 없었다면 "권장 기법이니 좋아졌겠지" 하고
> 넣은 채 넘어갔을 것이고, **그 뒤 M8·M9의 개선은 전부 나빠진 토대 위에서 측정됐을 것이다.**
> 유명한 기법이 내 데이터에서도 통한다는 보장은 없다.

**그래도 `heading_path` 자체는 유지한다.** 임베딩에 섞는 것과 저장·표시하는 것은 다른
결정이다. 저장된 값은 M10 인용 카드가 쓰고, `graph.py`의 출처 표기
(`[출처: CLAUDE.md > 아키텍처]`)는 모델에게 "이건 어느 절 이야기"를 알려준다.
**끈 것은 "임베딩 벡터에 섞는 것" 하나뿐이다.**

## 3. ★ M6가 지목한 두 건이 정확히 고쳐졌다 ★

전체 MRR은 0.791 → 0.794로 사실상 제자리다. **하지만 개별 항목은 크게 움직였다** —
`BASELINE-GENERATION.md` §5-1에서 "faithfulness는 개별 항목의 이동으로 읽으라"고
적어둔 그 원칙이 여기서도 그대로 적용된다.

| id | 질문 | M3 | **M7** | |
|---|---|---|---|---|
| `n02` | 마이그레이션은 컨테이너가 뜰 때 자동 실행되나? | ✗ | **1위** | ★ M6가 지목 |
| `n05` | alembic은 DB 접속 문자열을 어디서 읽나? | ✗ | **4위** | ★ M6가 지목 |
| `n01` | 파이썬 버전은 어떻게 관리해? | 2위 | 1위 | |
| `n03` | VITE_API_URL은 언제 정해지나? | 1위 | 2위 | |
| `n06` | 백엔드 테스트는 어떤 DB로? | 1위 | 3위 | |
| `n12` | uv sync는 어떤 방식으로 설치? | 3위 | **✗** | 잃음 |
| `k04` | `read:packages` | 5위 | **✗** | 잃음 |

**M6 베이스라인이 "M7이 고쳐야 한다"고 지목한 `n02`·`n05`가 정확히 고쳐졌다.**
`n05`는 생성 층에서 과잉 거절(문서에 있는데 "없다"고 답함)을 유발하던 바로 그 질문이다.

대신 `n12`·`k04`를 잃었다. 청크가 78 → 144개로 늘고 평균 크기가 210 → 133토큰으로
줄면서 **키워드 주변 문맥이 얇아진** 것이 원인으로 보인다. `k04`는 원래 M8(하이브리드
검색) 담당이라 예정된 자리에서 다시 다룬다.

> **전체 평균만 봤다면 "M7-1은 효과 없음"으로 결론 내고 넘어갔을 것이다.**
> 실제로는 목표한 두 건을 고치고 다른 두 건을 잃은, 성격이 전혀 다른 결과다.

## 3-1. ★ 생성 층이 검색 층을 1:1로 확인해줬다 ★

같은 골든셋으로 `evals.judge`를 다시 돌렸다.

| 종류 | n | faithfulness | relevance | 거절률 |
|---|---|---|---|---|
| normal | 12 | 4.67 → **4.75** | 4.92 → **5.00** | 0.08 → 0.08 |
| keyword | 7 | 4.43 → 4.29 | 5.00 → 4.71 | 0.00 → **0.14** |
| unanswerable | 5 | 4.80 → **5.00** | 4.80 → **5.00** | **1.00 → 1.00** |

**개별 항목을 보면 인과가 완전히 닫힌다:**

| id | 검색 층 | 생성 층 |
|---|---|---|
| `n05` | ✗ → **4위** | 거절 **O → −** (과잉 거절 해소) |
| `k07` | 1위 유지 | faithfulness **3 → 5** (환각 사라짐) |
| `n12` | 3위 → **✗** | 거절 **− → O** (새 과잉 거절) |
| `k04` | 5위 → **✗** | 거절 **− → O** (새 과잉 거절) |

**검색이 정답 대목을 가져오면 모델이 답하고, 못 가져오면 모델이 정직하게 거절한다.**
M6에서 `n05` 하나로 관찰했던 인과가, 이번엔 네 건에서 **양방향으로** 확인됐다 —
고쳐진 쪽(`n05`)과 새로 깨진 쪽(`n12`·`k04`) 둘 다.

이게 두 층을 나눠 측정한 값이다. 생성 지표만 봤다면 "거절률 0.08 → 0.08, 제자리"로
보였겠지만, **실제로는 거절하는 질문이 `n05`에서 `n12`로 바뀐 것**이다. 원인도 처방도
완전히 다른 상황인데 숫자 하나로는 구분되지 않는다.

**부수 소득 — `unanswerable`이 만점이 됐다** (faithfulness 4.80 → 5.00, 거절률 1.00 유지).
청크 경계가 문단을 존중하니 "관련은 있지만 답은 아닌" 발췌가 줄었고, 모델이 지어낼
빌미도 줄었다. M10이 지켜야 할 숫자가 더 좋아진 상태에서 시작한다.

## 4. 청킹 자체는 확실히 나아졌다

지표와 별개로, **청크의 물리적 품질**은 측정 가능하게 개선됐다:

| | M3 | M7 |
|---|---|---|
| 경계 기준 | 600자마다 무조건 | 마크다운 헤더 → 코드펜스 → 빈 줄 → 줄 → 공백 |
| 길이 단위 | 문자 (언어별 3배 편차) | **e5 토큰** (임베딩 한도와 같은 단위) |
| 청크 수 | 78 | 144 |
| 토큰 분포 | 158~264 (측정 안 했었음) | 4~215, 평균 133 |
| e5 512토큰 초과 | 알 수 없었음 | **0개** (매 인입마다 출력) |
| 메타데이터 | `source`, `chunk_index` | + **`heading_path`**, `token_count` |

**3-1의 "600자 청크가 512토큰 한도에 조용히 잘릴 수 있다"는 걱정은 실제로는 일어나지
않았다** — 실측해보니 최대 264토큰이었다. 걱정을 숫자로 바꾸면 그 걱정이 근거 없었음도
드러난다.

**남은 문제: 최소 4토큰짜리 청크가 있다.** 헤더 하나만 있고 본문이 거의 없는 섹션이
그대로 청크가 된다. 검색 잡음이고, 병합 로직이 필요하다 — **M7-3(Contextual Retrieval)
전에 이걸 먼저 손보는 것이 순서로 보인다.**
