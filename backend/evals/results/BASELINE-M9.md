# M9 대화형 질의 재작성 (2026-09-08)

M8 결과는 [`BASELINE-M8.md`](./BASELINE-M8.md).

---

## 1. ★ 먼저 얼마나 처참한지부터 쟀다 ★

골든셋에 `multiturn` 5건을 추가했다. `{"history": [...], "question": "그거 프로덕션에서는?"}`
형태로, **앞 대화를 모르면 답할 수 없는** 질문들이다.

**재작성 없이** 그대로 검색하면:

| 종류 | n | hit@1 | hit@5 | MRR |
|---|---|---|---|---|
| normal | 12 | 0.67 | 0.92 | 0.771 |
| keyword | 7 | 1.00 | 1.00 | 1.000 |
| **multiturn** | 5 | **0.20** | **0.40** | **0.300** |

**5건 중 1건만 1위, 절반 이상은 top-5에도 못 든다.**

> **M6~M8의 골든셋은 전부 단발 질문이라 이 실패를 한 번도 잡아내지 못했다.**
> 검색 MRR이 0.974까지 올라가는 동안, 실제 사용자가 두 번째 질문을 던지는 순간
> 0.300으로 떨어지는 구멍이 있었고 지표는 그걸 몰랐다. **골든셋이 못 보는 것은
> 존재하지 않는 문제처럼 보인다.**

## 2. 재작성 후

| 종류 | n | hit@1 | hit@5 | **MRR** |
|---|---|---|---|---|
| normal | 12 | 0.67 | 0.92 | 0.778 |
| keyword | 7 | 1.00 | 1.00 | 1.000 |
| **multiturn** | 5 | **1.00** | **1.00** | **1.000** |
| 전체 | 24 | 0.83 | 0.96 | **0.889** (0.743 → ) |

**multiturn 5건 전부 1위. MRR 0.300 → 1.000.**

**그리고 `normal`·`keyword`가 그대로다** — README가 경고한 *"재작성이 단발 질문을
망치는 회귀"* 가 일어나지 않았다. **조건부 실행 덕이다**: 히스토리가 없으면
`rewrite_query`가 LLM을 **아예 안 부르고** 원문을 그대로 돌려준다.
"항상 재작성"이었다면 첫 턴마다 지연이 늘고 뉘앙스가 죽을 위험을 졌을 것이다.

## 3. 설계 — 노드 하나 + 엣지 두 개

```
START → rewrite → retrieve → call_model ⇄ tools
```

**M2에서 StateGraph를 직접 조립한 값이 여기서 회수된다.** 함수 호출 사슬로 짜놨다면
이 삽입이 아팠을 것이다. 실제 변경은:
- `graph.py`에 `rewrite` 노드 하나
- `START → retrieve`를 `START → rewrite → retrieve`로
- `State`에 `search_query` 필드 하나

**★ `search_query`를 State에 따로 둔 이유 ★** 원문은 `messages`에 그대로 남아야 하고
(모델은 사용자가 **실제로 한 말**을 봐야 한다), 검색은 재작성본을 써야 한다 —
**두 값이 다른 일을 한다.** 하나로 합치면 *"왜 이 질문에서 검색이 실패했지"* 를 추적할 때
원문을 잃는다. README가 *"실제 실패 원인의 상당수가 재작성 단계에서 생긴 왜곡"* 이라고
경고한 그 추적이 불가능해진다.

**`rewrite_fn`도 인자로 뺐다** (`build_graph(model, retrieve_fn, ..., rewrite_fn)`).
없으면 원문을 그대로 쓴다 — 그래서 **기존 테스트 71개가 한 줄도 안 바뀌고 통과한다.**
`retrieve_fn`·`checkpointer`·`tools`와 완전히 같은 패턴이다.

**멀티쿼리 확장은 넣지 않았다.** README의 M9 계획에 있지만, 재작성만으로 multiturn이
MRR 1.000이 되어 **올릴 여지가 없다.** 넣으면 질문당 검색이 3배가 되어 지연만 늘고
지표는 그대로다 — **"측정하고 넣는다"는 원칙이 여기서는 "넣지 않는다"로 나온다.**
골든셋이 더 어려워지면(문서가 수십 개로 늘거나 애매한 질문이 들어오면) 그때 다시 잰다.

## 4. ⚠ Anthropic 크레딧 소진 — 측정 중단

M9 측정을 마치고 **전체 스택(재작성 + 하이브리드 + 리랭킹)** 을 재는 도중 API 크레딧이
소진됐다.

```
anthropic.BadRequestError: 400 - Your credit balance is too low to access the Anthropic API.
```

**그래서 이 문서의 §2까지는 유효하고, 전체 스택 숫자는 아직 없다.**

### 다만 — 폴백 설계가 실제로 검증됐다

크레딧이 끊긴 직후의 실행에서 **에러가 전파되지 않았다.** 대신:
- `rewrite_query`가 예외를 잡아 **원문으로 검색**했고
- `rerank`가 예외를 잡아 **검색 순서를 그대로** 썼고
- 지표는 재작성 없는 값(multiturn MRR 0.300)으로 **조용히 돌아갔다**

의도한 대로다 — *"재작성/리랭킹은 있으면 더 좋은 단계지 필수 경로가 아니다."*
**계획한 폴백이 진짜 장애에서 작동하는 것을 본 것은 처음이다.**

동시에 **이것이 폴백의 위험**이기도 하다: 지표가 조용히 나빠지는데 **에러는 안 난다.**
`--rerank` 실행 결과가 M8 때보다 나쁘게 나왔는데, 코드가 퇴보한 것이 아니라 API가
죽어 있었던 것이다. 로그(`logger.exception`)에는 남지만 **지표 표에는 안 보인다** —
M13에서 "리랭킹 실패율"을 지표로 올려야 할 이유다.
